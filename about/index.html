What Drop actually does, and doesn't do.

Drop is an accountless, short-term file sharing tool. This page explains the codebase directly—from the moment you pick a file, until the recipient finishes downloading and the server wipes everything. Plus why the server core runs C++ instead of offloading everything to Node.js.

01 · System Architecture

Who can see what?

The most critical detail: your files are encrypted locally inside your browser before anything leaves. The server only receives encrypted ciphertext and a lookup index used to locate it—the decryption share code is never sent to the server.

File contents and metadata (filename, type, etc.) are encrypted with AES-GCM inside the browser before sending. The server only stores ciphertext bytes with zero plaintext.

Why put it after the #

The short link's 22-character random token sits after the URL fragment identifier (#). Browsers never send hash fragments in HTTP requests, so the server never sees it. The recipient page converts it to a share code locally.

02 · Selection, Encryption & Upload

Files are chunked and encrypted before leaving your device.

You can select or drag and drop single or multiple files. The frontend verifies that your browser can still read those files before establishing an upload session with the server. The process never merges files into a single giant archive first—each chunk is transmitted as soon as it's encrypted.

01

Selection & Verification

The frontend reads a tiny slice of each file to verify accessibility. If a file was moved or lost permissions after selection, this step catches it and alerts you immediately.

02

Session Negotiation

The browser sends each file's size, expected chunk count, and encrypted metadata to the server. The server responds with a session ID, expiration time, and target chunk size.

03

Chunk & Encrypt

Each file is split into 64 MiB chunks. Each chunk is encrypted with AES-GCM inside an isolated Web Worker, running up to 3 parallel threads to balance speed and memory usage.

04

Transfer Ciphertext & Finalize

Each ciphertext chunk is sent along with its unique IV. Once the server verifies size matching and all chunks arrive, the session is marked as ready for download.

What a single chunk goes through during encryption

A closer look at a single chunk: plaintext exists only on your device, while the network and server see only ciphertext.

AES-GCM provides both confidentiality and integrity: without the correct key, ciphertext is gibberish; if ciphertext, IV, or auth tag is tampered with, browser decryption fails with an error instead of silently outputting corrupted data.

03 · Keys, Share Codes & Data Derivation

Deriving multiple distinct values from a single secret.

This is where confusion often arises: share code, AES key, server lookup index, and download token are NOT the same value. Each has a dedicated purpose, and the frontend prefixes distinct purpose strings during hashing to prevent cross-domain misuse.

A

22-Char URL Token

Generated via browser cryptographically secure random bytes using unbiased Base62. Exists only after the URL # for the recipient.

Shared with recipient
B

64-Char Share Code

Derived by SHA-256 hashing A with a "share-code" purpose tag. Can also be copied and pasted manually by the recipient.

Sender & Recipient Browsers
C

AES-256 Key

Derived by SHA-256 hashing the share code again. The resulting 256-bit key is imported directly into the Web Crypto API.

Used only during browser crypto ops
D

Lookup Index

Derived by SHA-256 hashing the share code with a "lookup" tag. Sent to the server to locate ciphertext. This index cannot decrypt data.

Sent to Server

Hashing is not encryption. SHA-256 is one-way—you can compute the lookup index from the share code, but you cannot reverse it. The server uses the lookup index to find records without ever knowing the share code.

What does the frontend send during upload?

Three phases: session initialization, chunk transmission, and completion signaling.

Session Init
Lookup index, file ID, original size, total chunk count, and encrypted metadata (filename, mime type, size) with its IV.
Per Chunk
Encrypted binary payload, chunk IV, and byte size. IVs are not secret, but must accompany their ciphertext.
Completion
A completion signal with session ID. The server verifies all chunks are accounted for before enabling downloads.

What is exchanged during download?

Acquiring an ephemeral download session, then fetching ciphertext chunk by chunk.

Download Init
Browser sends the lookup index. Server returns a download ID, temporary lease token, and encrypted metadata.
Per Chunk
Browser presents the lease token for a specific chunk; server streams ciphertext with IV in response headers.
After Save
Browser notifies the server "save complete", triggering deletion. Deletion happens after confirmed save, not at download start.

Local Storage Note: The sender page saves the latest share code, link, and expiration in localStorage for convenience when reopening windows. Manually entered download codes use sessionStorage. If using a shared computer, close tabs or clear browser data. Watch out for clipboard managers and browser extensions.

04 · Retrieval, Expiration & Deletion

Confirm local save complete before triggering server deletion.

Simply opening a link only checks availability without consuming the share. Actual downloads decrypt and write all chunks to your designated location first; only upon complete success does the frontend instruct the server to delete.

  1. 1

    Derive Keys Locally

    The recipient page computes the AES key and lookup index locally from the URL fragment or pasted 64-char share code—never sending them to the server.

  2. 2

    Check Availability

    The page queries availability using the lookup index without creating a download session or triggering deletion.

  3. 3

    Acquire Lease Token

    Starting a download transitions the session to "downloading" and issues an ephemeral lease token required for each chunk request.

  4. 4

    Decrypt & Stream to Disk

    The browser receives ciphertext and IV, immediately decrypting and writing to disk—either directly, to a temp file, or via ZIP stream for multiple files.

  5. 5

    Signal Deletion After Save

    Only after all file handles close successfully does the frontend issue a deletion call. If cancelled or interrupted, no deletion signal is sent, allowing retries before expiry.

Interrupted Upload or Tab Closed

The frontend sends a best-effort abort notification. If upload fails, the session is cancelled. The server removes incomplete sessions and zero-wipes ciphertext memory.

Best-effort notification; network loss unguaranteed

Download Succeeded

The server revokes the lookup index first, then deletes the session. In-flight chunk streams are marked "pending deletion" and purged immediately upon response end.

Deleted only after save confirmation

Automatic Expiration

Default 30-minute lifespan with at least minute-level cleanup scans. Activity resets idle timers, acting as an idle timeout rather than a hard wall.

Wiped upon expiry with memory return attempted

Admin "Purge All"

An admin route provides an instant "wipe all data" button, clearing all sessions. Note: this route currently has no auth; restrict access at the network layer when deploying.

Global purge across all active shares

Legacy Fallback Route: Modern transfers use chunking, but legacy JSON upload/download APIs remain in the codebase as a fallback. The legacy route deletes data immediately upon download start rather than waiting for save confirmation.

05 · Understanding Memory from First Principles

"Unsetting a variable" and "data is erased" are two different things.

This isn't a JavaScript defect; high-level managed languages are designed this way. Understand where data lives in memory before discussing why Garbage Collection cannot give you deterministic zero-wiping control.

Stack: Call Stack

Like a stack of task notes

Executing FunctionLocal variables & references to large objects
Caller FunctionParent scope frame
Earlier FunctionsAwaiting return

When a function is invoked, its stack frame is pushed to the top; upon return, the frame pops immediately.

Reference

Heap: Dynamic Memory

Like a reusable warehouse

ObjectsMetadata & session state
Byte BuffersCiphertext, raw data, or copies
Other AllocationsWaiting for future reuse

Large objects and buffers live on the Heap. Stack variables hold references to them, but popping a stack frame does not overwrite Heap bytes.

1

Function return does not mean data erasure

JavaScript functions allocate objects or byte buffers. When a function finishes, its stack frame vanishes, but heap objects remain alive as long as references exist. Unreferenced objects are merely "eligible for GC"—not zeroed out.

2

GC execution timing is non-deterministic

Node.js runs on V8. Garbage collection runs when V8 decides the time is right. Your application cannot force immediate GC, nor demand that V8 overwrite bytes before recycling.

3

Setting variables to null does not zero memory

Assigning null drops a reference pointer; deleting object keys alters layout. Unless your code explicitly overwrites buffer memory, old bytes sit on the heap until overwritten by future allocations.

4

Heap dump leakage risk

If an attacker gains memory access (host compromise, debug tools, core dump), residual heap bytes can be extracted. For servers, this includes active ciphertext or temporary buffers; for plaintext handling, the risk is severe.

Typical lifecycle of GC-managed data

Conceptual overview; exact timing varies per execution state.

Active Use

App holds buffers; data is readable.

References Lost

App drops pointers, but bytes are not zeroed.

Non-Deterministic GC

Future Reuse / Return

06 · Why the Server Core Runs C++

To guarantee deterministic erasure timestamps for ciphertext.

Node.js handles HTTP, routing, CORS, and validation. But persistent ciphertext containers live inside a C++ native addon—not because C++ is inherently immune to bugs, but because C++ allows explicit zero-overwrite and deallocation semantics bound strictly to object lifecycles.

C++Native security core

Standard Node.js / V8 Buffers

  • Object recycling timing is controlled entirely by V8 GC.
  • Dropping JS references leaves raw bytes intact in memory.
  • Intermediate heap copies have unpredictable lifetimes.
vs

Drop's C++ Persistent Ciphertext Containers

  • Ciphertext, IVs, and metadata use non-copyable secure byte containers.
  • Container reset or destruction executes compiler-barrier zero-fill overwrites.
  • Session deletion, expiry, failure, or purge immediately triggers zeroing and page return requests (glibc malloc_trim).
1Receive

Node stream ciphertext is copied into C++ dedicated memory.

2Store

Containers are move-only, preventing unnecessary heap copies.

3Stream

In-flight downloads use lease refcounts, holding memory until response closes.

4Purge

On error, expiry, completion, or purge, bytes are zeroed before free.

The C++ core performs no AES operations and never sees plaintext; it strictly manages ciphertext lifecycles. This removes persistent server copies without waiting for V8 GC, though ephemeral socket or OS buffers are beyond native addon scope.

Summary

Decryption stays in your browser; ciphertext is temporarily cached on a short-lived server.

Your browser encrypts with AES-GCM and fresh IVs per chunk; share codes are never transmitted; the server operates on one-way lookup indices; the C++ core actively zero-wipes ciphertext upon session termination. These engineering decisions minimize residual server exposure—though endpoint security and deployment hygiene remain essential.
